I spent an afternoon staring at a Python process that wasn't doing anything. No error, no crash, no output, just a frozen terminal. The pipeline was supposed to take a compiled C binary, lift it through Ghidra, and produce an attributed control flow graph. Instead, it hung indefinitely. The culprit wasn't my code, wasn't Ghidra, and wasn't even the binary format. It was the space between Python and the JVM.

## Two compilers, two binary worlds

Every compiled C file in this project lands in one of two formats, determined entirely by which compiler produced it.

When I compile on my MacBook Air (M1, Apple Silicon) with the system `gcc`, which is actually Apple Clang, the output is a **Mach-O** binary targeting ARM64:

```
$ gcc -c file.c -o file.o
$ file file.o
file.o: Mach-O 64-bit object arm64
```

When I compile with the cross-compiler toolchain the project uses for training, the output is an **ELF** binary targeting x86-64:

```
$ x86_64-elf-gcc -c file.c -o file.o
$ file file.o
file.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV)
```

These are fundamentally different formats: different headers, different section layouts, different relocation models. And on this machine, they take different paths through the pipeline for a reason that took me hours to isolate.

## The symptom: one method hangs, the other doesn't

Ghidra 12.1.2 handles both formats just fine. It ships with processor modules for `AARCH64` and `x86` and can load, disassemble, decompile, and analyze either one. The problem isn't what Ghidra can do, it's how Ghidra gets invoked from Python.

There are two ways to drive Ghidra programmatically, and they behave differently on this machine:

| Method | How it works | Mach-O ARM64 | ELF x86-64 |
|--------|-------------|-------------|------------|
| **pyghidra** | Ghidra's JVM runs inside the Python process, bridged via JPype | **Hangs — never returns** | Works |
| **analyzeHeadless** | Ghidra runs as a separate Java subprocess, communicates via filesystem | Works | Works |

Both methods run the same Ghidra engine under the hood. The difference is architectural.

**pyghidra** starts a JVM inside the Python process using JPype, loads Ghidra's Java classes into that embedded JVM, and calls Ghidra APIs directly. Python and Java share the same process, where function calls cross the language boundary through JPype's bridge layer, but memory, threads, and signal handlers all coexist in one address space.

**analyzeHeadless** spawns a completely independent Java process (`java -jar ghidra.jar ...`). Python and Ghidra only communicate through the filesystem: Python writes the input binary to disk, Ghidra reads it, Ghidra writes JSON output to disk, Python reads it back. They're separate processes with separate memory, separate threads, and no runtime coupling.

## The root cause: a deadlock in the JPype bridge

The Mach-O hang is specific to the JPype layer. Something about loading a Mach-O ARM64 binary triggers a deadlock or infinite wait inside the JPype-embedded JVM, one that never occurs when the same JVM runs standalone in analyzeHeadless mode.

I never fully root-caused the exact lock. Ghidra's Mach-O loader for AARCH64 in version 12.1.2 performs several operations that touch both the native filesystem layer and Java's classloader concurrently, and JPype's thread model doesn't perfectly replicate a standalone JVM's threading guarantees. Some interaction between Ghidra's native loader, the JVM's signal handling, and JPype's Python-to-Java call marshalling creates a circular wait. ELF loading doesn't hit the same code path, so ELF binaries sail through pyghidra without issue.

This is the kind of bug that's hard to reproduce in isolation, it depends on the exact combination of Ghidra version, JDK version, JPype version, and the target binary's architecture. And it's invisible: no stack trace, no timeout, just a process that stops making progress.

## Why it worked on Eric's machine

Eric's `export.py` uses `GhidraGG.multiprocess_files()` with native Mach-O binaries and it runs fine. There are a few plausible explanations, none mutually exclusive:

**Architecture difference.** If Eric is on an Intel Mac, his Mach-O binaries are x86-64, not ARM64. The JPype hang may be specific to the AARCH64 Mach-O code path, which his machine never exercises.

**Ghidra version.** Eric may be running a different version of Ghidra where the bug doesn't exist, or where the loader's concurrency pattern avoids the deadlock.

**Java version.** The JPype-JVM bridge behaves differently across JDK versions. A different JDK, even a different minor version, can shift thread scheduling enough to mask or trigger the issue.

The important thing is that these differences don't matter for the pipeline. They're handled.

## The fix: detect and route

`pipeline.py` doesn't assume anything about the binary you give it. It inspects the file header, detects the format, and routes accordingly:

- **ELF** -- pyghidra (Path 1). This is the fast path. Richer graphs, faster extraction, and it matches the training environment exactly.
- **Anything else** -- Mach-O, PE, raw binary → analyzeHeadless (Path 2). Slower, but produces valid results every time.

The ELF path is preferred because it preserves the full graph fidelity the GNN was trained on. But the Mach-O path produces graphs in the same 84-feature vector space, encoded by the same model. Cosine similarity comparisons between a Mach-O-imported reference and an ELF-imported target are valid: the graph representation is format-agnostic after extraction.

This also means the default reference binary (`fill_ref_O0.o`, which is Mach-O) works fine. It goes through Path 2 automatically. If you recompile it as ELF with `x86_64-elf-gcc -O0 -c fill_ref.c -o fill_ref_elf.o`, both reference and target take the fast path. Either way, the output is comparable.

## Practical workflow

For day-to-day local work on this machine, the simplest approach is to compile everything as ELF with the cross-compiler. Both binaries take Path 1, runtime is fastest, and graphs are highest fidelity:

```
x86_64-elf-gcc -O0 -c reference_func.c -o ref_O0.o
x86_64-elf-gcc -O3 -c target_program.c -o target_O3.o
python pipeline.py target_O3.o --ref ref_O0.o
```

But if you already have pre-compiled Mach-O binaries, just pass them directly, the headless fallback handles them without any extra flags:

```
python pipeline.py target_O3.o --ref fill_ref_O0.o
```

It's slower (30–90 seconds per binary) but produces equivalent results.

When sharing work with Eric, his `export.py` handles Mach-O natively on his machine. If you need to run his extraction code on this machine, either recompile the binaries as ELF first, or use `pipeline.py` instead, as it handles both formats through the routing logic.

---

The broader lesson here isn't really about Ghidra or Mach-O binaries. It's that JVM embedding is fragile in ways that are hard to anticipate and harder to debug. When you fuse two runtimes into one process, you inherit the intersection of their assumptions about threading, memory, and signal handling; and when those assumptions conflict, you don't get an error message. You get silence. The fix was to stop fighting the embedded JVM and let Ghidra run the way it was designed to run: in its own process, on its own terms.
